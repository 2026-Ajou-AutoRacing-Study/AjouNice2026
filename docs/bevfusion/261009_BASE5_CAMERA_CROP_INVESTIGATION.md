# Base5 BEVFusion 카메라 crop 분석과 입력 후보

2026-10-09 16:56 KST 원본 snapshot 기준. CPU 분석의 우선 후보는 448×896 아래 정렬이며,
비용 우선 후보는 384×896, 원거리 픽셀 밀도 확대 후보는 512×1056이다.
최종 학습 설정은 전처리 정합과 GPU 비용 검증 후 확정한다.

목표는 원거리 차량과 작은 장애물의 영상 단서를 유지하면서 근접 차량, 측방 통과,
사람과 복합 객체의 잘림을 줄이는 것이다. 입력 픽셀 수, 남기는 원본 영역, 카메라별
시야를 구분하여 검토한다. 현재 Sunny13 수집과 production E25는 변경하지 않는다.
본학습을 후보별로 여러 번 완료하는 계획도 아니다.

이 문서는 crop과 resize 설계의 조사 기준이다. GPU 비용 시험과 팀원 전달 번들은
[4090 추가 비용 시험 계획](261009_BASE5_CAMERA_INPUT_AND_4090_BENCH_PLAN.md)을 따른다.
가중치 초기화와 pooling/cache 구현 순서 및 수집 중 제한된 CUDA 시험 경계는
[초기화·연산 최적화 계획](261009_BASE5_INITIALIZATION_AND_RUNTIME_OPTIMIZATION_PLAN.md)을 따른다.

## 현재 자르는 방식

크기는 모두 높이×너비다. 원본을 같은 가로세로 배율로 resize하고, 최종 입력 높이만큼
아래에서부터 남기는 고정 bottom crop이다. 객체 위치를 찾아서 따라가는 crop이 아니다.
현재 고정 배율에서는 최종 너비와 resize 너비가 같아 별도의 좌우 crop은 거의 없다.

| 카메라 | 원본 | Base5 320×896 후보의 resize | 남기는 원본 세로 영역 |
|---|---|---|---|
| 전방 CAMERA_1 | 720×1280 | 약 504×896 | 약 36.5%부터 아래 끝까지 |
| 좌전방 CAMERA_2 | 480×640 | 약 672×896 | 약 52.4%부터 아래 끝까지 |
| 우전방 CAMERA_3 | 480×640 | 약 672×896 | 약 52.4%부터 아래 끝까지 |
| 후방 CAMERA_4 | 720×1280 | 약 504×896 | 약 36.5%부터 아래 끝까지 |

비율은 픽셀 높이이며 시야각 비율이 아니다. 정수 resize와 crop 반올림에 따른 경계 차이는
별도로 확인한다. 위 표는 **Base5 후보와 수집 audit의 320 기준**이며, 현재 production E25의
입력을 320으로 바꿨다는 뜻이 아니다. E25는 256×704 입력을 사용한다.

코드의 기본 식은 다음과 같다.

```python
resize = base_resize * reference_width / native_width
new_width, new_height = int(native_width * resize), int(native_height * resize)
crop_top = int((1 - bot_pct) * new_height) - final_height
crop_left = int(max(0, new_width - final_width) / 2)
```

현재 bot_pct는 0이므로 crop_top 위쪽을 제거하고 아래 끝까지 남긴다.
원본 카메라 종횡비가 서로 달라, 같은 출력 크기로 만들더라도 잘리는 원본 영역은 다르다.

## 카메라별 설정 가능 범위

카메라별로 서로 다른 원본 영역을 잘라서 **동일한 출력 크기**로 만드는 방식은 가능하다.
각 카메라의 resize와 crop을 img_aug_matrix에 기록하고 학습과 온라인이 같은 처리를 해야 한다.
출력 크기가 같으면 crop 위치 변경 자체로 모델 입력 픽셀 수가 늘어나지는 않는다.

다만 현재 MoraiImageAug3D는 카메라별 원본 크기를 읽지만 final_dim, resize_lim,
bot_pct_lim은 공통 설정이다. 카메라별 crop 위치를 지정하는 설정은 아직 없다.
Docker online 경로는 bot_pct가 0이 아닌 설정을 거부하며, ROS host 경로에는 E25의
256×704와 resize 0.55가 명시돼 있다. 새 config만 수정해서 모든 경로에 반영된다고
가정하면 안 된다.

전방은 384×1056, 측면은 448×640처럼 **서로 다른 출력 크기**로 직접 넣는 것은 별도 문제다.
현재 전처리는 네 영상을 stack하고, 모델도 공통 image_size와 feature_size로 처리한다.
패딩하거나 카메라별 연산을 나누는 확장이 필요하며, 패딩 영역의 depth와 BEV 기여도
처리까지 검증해야 한다. 이번 조사에서는 동일 출력 크기와 카메라별 crop을 먼저 검토한다.

전방과 후방 모두 이 집단의 원본 객체 픽셀을 90% 이상 남기는 비율은 이미 100%였다.

1056 너비로 늘리면 원거리 차량의 선형 크기는 약 18% 커져 전방 중앙값은 12.56픽셀,
후방은 11.91픽셀이 된다. 전방 mask 면적 중앙값도 94.5에서 131픽셀로 늘었다.
stride 8 기준 전방 차량 높이 약 1.33에서 1.57 feature cell 규모에 해당하는 단순 비교이며,
detector가 하나의 cell로만 물체를 인식한다는 뜻은 아니다.

반면 384×1056처럼 비슷한 종횡비만 유지하면 측방에서 잃던 시야가 거의 그대로다.
448×896은 384×1056과 거의 같은 픽셀 예산으로 더 넓은 세로 영역을 확보한다.
1056 너비의 밀도와 비슷한 시야를 함께 원하면 512×1056이 더 적절하다.
480×1056은 중간안이지만 절약하는 픽셀 예산은 512 대비 6.25%뿐이다.

### 다른 센서의 보완과 GT 재선별

센서 합산은 같은 3D component를 여러 카메라에서 중복 세지 않았다. camera ID를 공유해
component 구분이 불명확한 154개는 합산 분석에서 제외했으며 raw GT에서 삭제하지 않았다.
원본 camera-visible이고 구분 가능한 component 5,649개 중 LiDAR 0점은 419개였으며,
이 419개는 모두 후보 ROI의 center 범위 안에 있었다.

최종 입력 mask 16픽셀 이상과 잘린 2D 박스 최소 변 4픽셀이라는 진단 조건을 적용하면,
LiDAR 0점 객체에서 camera 조건을 통과하는 component는 320×896 아래 정렬 308개,
448×896 344개, 512×1056 363개다. 기준 후보 대비 각각 36개, 55개가 추가 통과했다.
원본 mask를 nearest resize한 진단 값이며 실제 RGB interpolation이나 최종 라벨 결과는 아니다.
저장된 audit의 resize 반올림 및 mask 방식과 경계 차이가 있어 저장 positive 수와도
정확히 일치하지 않는다. 새 GT 개수를 위 숫자로 확정하지 않는다.

새 입력으로 학습하기 전에는 raw annotation에서 visibility와 info를 다시 구성해야 한다.
기존 320 기준의 positive flag를 그대로 쓰면 새 crop에서 보이는 camera-only 객체를
배경으로 취급할 수 있다. 3D 중심과 크기는 캡처 annotation 그대로 유지하고, 2D crop에
맞춰 3D box를 줄이지 않는다. component 매칭이 애매한 복합 객체는 기존 분리 정책을 유지한다.

## 추천 입력과 남은 검증

**첫 비용 시험의 우선 후보는 448×896 아래 정렬**이다. 너비 확대보다 근접·측방의
시야 손실을 먼저 줄이며 현재 공통 bottom crop 구조를 유지할 수 있다. 4090 비용이나
학습 VRAM이 부족하면 384×896으로 낮춘다. 원거리 픽셀 밀도까지 높일 예산이 확인되면
512×1056을 비교한다. 384×1056 아래 정렬이나 448×1248처럼 기존 비율만 유지한 확대를
우선 후보로 삼지 않는다. 위치만 올린 320도 근접 장애물 손실 때문에 주 추천에서 제외한다.

| 추천 순서 | 입력 | 의도 | 4090 모델 평균 비용의 단순 외삽 |
|---|---|---|---:|
| 비용 우선 대안 | 384×896 아래 정렬 | 최소한의 측방 시야 복원 | 약 52ms |
| 우선 후보 | 448×896 아래 정렬 | 근접과 측방 시야를 넓게 보존 | 약 58ms |
| 원거리 밀도 확대 대안 | 512×1056 아래 정렬 | 비슷한 시야와 더 많은 원거리 픽셀 | 약 72ms |

시간은 기존 4090의 320×896 모델 평균 45.86ms에서 이미지 관련 29.78ms만 픽셀 수에
비례한다고 가정한 추정이다. 후보 실측이나 4-class Base5의 처리시간이 아니다.
CPU 준비와 ROS, publish는 미포함이며 유효 depth pooling 밀도도 crop에 따라 달라질 수 있다.
512×1056은 13Hz의 약 76.9ms 주기에 여유가 작을 수 있어 p95와 end-to-end 확인이 특히 필요하다.
학습시간 배수는 추론 외삽으로 확정하지 않고 실제 backward와 optimizer step을 측정한다.

전체 원본 letterbox는 시야는 보존하지만 padding과 객체 픽셀 축소가 생긴다. 카메라별
다른 출력 shape나 비균일 resize는 pretrained 외관과 공통 frustum, 패딩 처리를 추가로
바꾸므로 대회 직전 우선 구현하지 않는다. 같은 shape의 높이 확대를 먼저 검증한다.

다음은 추천 후보의 학습·Docker raw·ROS prepared 전처리를 동일하게 만들고 실제 입력
및 LiDAR 투영을 대조하는 단계다. 현재 분석의 img_aug_matrix 역변환 단위 검사는 통과했지만
세 runtime 경로의 정합을 인증한 것은 아니다. 수집은 유지하며 비용 실측은 별도 4090 또는

## 거리와 해상도에 관한 가설

낮은 객체가 영상 아래쪽에 있고 큰 근접 객체가 세로를 많이 차지할 수 있다는 가설은
분포별로 확인한다. **멀리 있는 차량도 항상 아래쪽에 있는 것은 아니다.** 이번 높이 분포에서는
영상 중간에 관측이 집중됐으며, 객체 위치는 카메라 장착 높이와 pitch, 거리, 지형에 좌우된다.
아래쪽만 높은 해상도로 남기면 원거리 차량의 단서를 오히려 버릴 수 있다.

정사각형에 가까운 입력이 근접과 측면에 유리한지는 원본에서 실제로 더 넓은 세로 영역을
남기는지로 판단한다. 입력의 비율만 바꾸거나 잘린 영상을 늘리는 것으로는 없어진 부분이
돌아오지 않는다. 측면 640픽셀 원본을 896픽셀 이상으로 확대해도 새 원본 정보가 생기지 않는다.
다만 모델의 feature sampling 밀도와 세부 인식 효과는 별도 실험으로 판단한다.

현재 후보군은 bottom crop 기준, 동일 크기에서 카메라별 위치 조정, 너비를 유지한 세로
확대, 같은 영역의 고해상도화다. 전체 원본을 담는 letterbox나 다른 종횡비도 보조 비교하되
유효 픽셀 감소와 패딩을 평가한다. 서로 다른 카메라 출력 크기나 영역별 비균일 확대는
공통 tensor와 투영 설계 변경이 커서 앞선 후보가 부족할 때 검토한다.

이미지 입력 종횡비와 BEV의 종횡 범위는 별개다. 이미지가 정사각형에 가까워져도
종방향 ±100m와 횡방향 ±30m의 BEV를 정사각형으로 변경할 이유는 없다.

## 조사 순서와 변경 경계

1. 수집 중에는 저장된 snapshot과 소량의 원본만 CPU로 분석한다. 원본 좌표와 실제
   객체 픽셀을 바탕으로 카메라별 crop 후보를 좁히고, 아래쪽 손실과 다른 센서의 보완을 확인한다.
   후속 사용자 합의로 작은 pooling 연산의 제한된 CUDA correctness 시험은 별도로 가능하다.
   전체 모델 로딩·학습·공식 latency 시험 허용을 뜻하지 않으며 위 실행 계획의 수집 보호 경계를 따른다.
2. 후보를 정한 뒤 학습과 두 online 경로의 전처리 및 투영 정합을 검증한다.
   이 단계는 새 설정의 시험이며 현재 collector와 E25 runtime을 교체하지 않는다.
3. 수집 종료 또는 별도 4090 환경에서 동일 sample과 고정 BEV 및 depth로 비용을 측정한다.
   본학습 전에 최종 입력 계약을 동결하고 raw로 GT와 info를 재계산한다.
4. 본학습 후 독립 mission rosbag으로 검증한다. 새 모델의 threshold도 이때 정하며
   기존 0.40/0.15/0.10을 새 모델의 최선이라고 가정하지 않는다.

원본과 annotation 및 객체 metadata가 보존된 범위에서는 crop 변경만으로 재수집하지 않는다.
현재 단계에서는 추천 후보를 좁혔으며 최종 해상도, runtime crop, 라벨 정책 변경은
전처리 정합과 비용 검증 후 결정한다.
