# v99에서 최적화 범위 60m와 90m의 실제 주행 비교

상태: EVIDENCE, 2026-10-28. 브랜치 `competition/final-readiness-261028`에서 수행했다.
**네 조건 모두 완주했지만 90m의 실주행 우위는 확인되지 않아 운영 설정은 60m로 유지한다.**
이 결정은 [기존 고정 입력 대조](261028_TEAM_LAN_AND_DUPLICATE_TRACK_REVIEW.md)의 초기 실패 감소를 부정하지 않는다.
고정 입력 재생과 새로운 센서·측위·제어 입력이 들어오는 폐루프 주행은 서로 다른 시험이다.

## 같은 조건과 달라진 값

실제 설치된 E12 추론·C++ tracker·Map-CV·측위·BPP/SOA·MPT·PP/PI 제어기를 사용했다.
기록된 지도 패킷과 활성 map loader·predictor·projector 모두 v99였다.
공식 START, 첫 두 경유점, 상자 뒤 약 56m의 목표를 고정했다. 차량은 약 59km/h까지 가속했다.
상자는 공식 샘플의 CargoBox 한 개와 위치·배율 `(2,3,2)`를 그대로 사용했다.
무장애물 조건은 같은 장면에서 그 상자만 제거했다. 다른 NPC·보행자·spawn·음영 객체는 없었다.

60m/90m 시험용 launch는 최적화의 `obstacle_optimization/max_forward_length`만 달랐다.
양쪽에 같은 MPT trace를 켰고, 실행 전에 전체 resolved 파라미터의 차이가 그 한 leaf뿐임을 검사했다.
값은 노드 생성 전에 설정했다. 실행 후 `rosparam set`으로 생성자 값을 바꿨다고 주장하지 않는다.
신호등은 이 장애물 대조에서 OFF였다. 추적 연구 후보 두 개도 OFF였다.
검출 threshold·NMS·안전 마진·SOA 기억·제동계수·지도는 변경하지 않았다.

## 네 번의 실제 결과

아래 시간은 validator의 동일한 `elapsed_sec`다. 초기 준비·종료 대기는 제외한다.
별도 감사의 `CONTROLLER_START`부터 `GOAL_REACHED`까지 시간은 시작 경계가 달라 수치를 혼용하지 않는다.

| 장면 | 60m | 90m |
|---|---:|---:|
| 무장애물 | PASS, 50.29초 | PASS, 50.57초 |
| 공식 확대 상자 한 개 | PASS, 53.86초 | PASS, 62.16초 |
| 충돌 | 두 시험 모두 0 | 두 시험 모두 0 |
| 실제 정지·P 종료 | 두 시험 모두 확인 | 두 시험 모두 확인 |

모든 bag은 정상 인덱스로 열렸고 영상도 정상 마감됐다. 실제 cap·후보 OFF·설치본 해시를 별도로 감사했다.
원본 전방 JPEG, Ego·GPS·IMU·측위, 검출·추적·association, SOA·MPT trace, 경로·제어·처리시간을 기록했다.
대용량 raw LiDAR·나머지 세 카메라는 제외했다. 따라서 raw 센서 전체 재추론용 녹화라고 부르지 않는다.

## 실패 로그와 실제 감속의 구분

무장애물 60m는 곡선에서 한 episode의 QP 실패 로그 4개와 이전 경로 유지 1개가 있었다.
그때 속도는 약 7.71→7.86m/s였고 브레이크는 0이었다. 실패 로그만으로 차량이 멈칫했다고 세지 않는다.
무장애물 90m에서는 해당 실패·fallback 로그가 없었다.

상자 60m는 상자가 약 60.2m 앞일 때 최종 충돌 검사에서 후보가 탈락하고 이전 경로 제동을 출력했다.
해당 cycle의 QP 두 번은 풀렸지만 최종 경로가 탈락했다. 이를 QP 자체의 infeasible과 구분한다.
이 초기 사건은 두 번째 추적 ID가 출력되기 약 1.9초 전이므로 중복 객체만으로 설명되지 않는다.
90m에서도 더 가까운 위치에서 실패와 이전 경로 제동이 남았다. 상자 주행의 fallback 로그는 양쪽 모두 3개였다.
지도 제한속도·회피 곡률도 감속에 영향을 주므로 모든 감속을 실패 로그 탓으로 돌리지 않는다.
목표 정차를 제외한 사후 분석 구간인 native 지도 Y330~430m에서 최저속도는 60m 약 15.85km/h,
90m 약 7.67km/h였다. 둘 다 0.2m/s 미만이 0.5초 이상 이어지는 중간 정지는 없었다.
제어 시작→목표 기준 약 8.91초의 차이는 상자 접근뿐 아니라 그 전후에도 나뉘어 발생했다.

| 상자 주행의 제어 활성 구간 | 60m | 90m |
|---|---:|---:|
| MPT 처리시간 p95 / 최대 ms | 54.53 / 133.14 | 49.77 / 152.60 |
| 최종 후보 없음 cycle | 13 | 12 |
| 실제 새 검출 Hz | 6.08 | 6.22 |
| 검출 입력 header→발행 age p95 ms | 391.62 | 324.43 |

평균적인 처리량 저하만으로 90m의 8.30초 증가를 설명할 수 없다.
실제 감지 입력도 서로 다르므로 검출·중복 개수 차이를 cap만의 효과라고 주장하지 않는다.

## 로컬 시뮬레이션 시간과 측위의 교란

MORAI와 추론을 같은 PC에서 실행했다. 두 상자 시험의 측위 설정·초기화·source/install 계약은 같았다.
원본 Ego·GPS·GNSS odom·Local에서는 이동 중 역방향 위치 step이 없었지만 Global에서는 차이가 있었다.
감사 기준인 `v>3m/s`에서 60m는 27회, 90m는 267회였고 Smooth 정합 reset도 많았다.

원본 Ego의 이동 경로는 약 383m로 비슷한데, 벽시계로 Competition 속도를 적분하면
60m는 약 476m, 90m는 약 521m였다. 실제 위치 진행/속도 적분 비율은 약 0.804/0.734였다.
무장애물에서는 약 0.826/0.818로 비슷했다. GPS header 수신 지연이 90m에서 더 크지는 않았다.
이는 로컬 시뮬레이션 위치 진행과 호스트 시간 기반 운동 예측의 불일치에 부합한다.
Unity의 직접 시뮬레이션 시계나 당시 전체 host 계측은 없으므로 정확한 real-time factor·CPU 원인으로 확정하지 않는다.
측위 보정이 플래너의 경로 재검증·주행 시간에 섞였을 가능성이 있어 90m 단독 원인으로 단정할 수 없다.

## 후속 동일 입력 재생에서 확인한 개선과 반례

실주행의 다른 입력·측위 진행을 분리하기 위해, 두 상자 bag의 MPT 입력을 그대로 고정해 재생했다.
도로 경계가 있는 smoothed path, 같은 정수 ns의 SOA scene, MPT가 실제 선택했던 odometry를 묶었다.
새 검출·측위를 계산하거나 차를 주행시키지 않고, 실제 설치 MPT만 격리 master에서 실행했다.
각 쌍은 cap 한 값만 다르며 입력 CRC·실제 사용 pose/twist/covariance·출력 sequence/CRC를 검증했다.
디버그 odometry header는 원래 센서 시각이 아니라 path에 맞춰진 키이므로 공동 취득 시각이라고 해석하지 않는다.

| 원본 입력 | 완전 입력 묶음 | 60m 실패 | 90m 실패 | 90m에서 회복 / 새 실패 |
|---|---:|---:|---:|---:|
| 60m 실제 주행에서 얻은 입력 | 696 | 13 | 6 | 7 / 0 |
| 90m 실제 주행에서 얻은 입력 | 800 | 11 | 12 | 2 / 3 |

각 원본의 60m·90m를 각각 두 번 실행한 최종 8회에서 위 실패 집합이 반복됐다.
두 번째 원본에는 실제 사용 odometry가 없는 path 한 개가 있어, 보간하지 않고 해당 header의 제외를 명시했다.
따라서 두 원본 전체가 같은 696개 입력이거나 무손실 raw 센서 재생이었다고 부르지 않는다.
각 원본의 BPP·측위에는 이미 당시 폐루프의 영향이 들어 있으며, 이 시험은 그 조건에서의 MPT 출력 대조다.

첫 원본에서 90m는 초기 멀리 있는 상자의 회피 경로를 만드는 데 도움이 됐다.
남은 6회는 두 객체 상태의 QP 미해결 2회와 측정 차체의 현재 도로 경계 이탈 4회였다.
그러나 다른 원본에서는 90m의 새 실패가 생겼다. 첫 반례의 신규 후보는 양쪽 모두 도달 불가였지만,
60m는 이전 경로가 현재 충돌 검사를 통과해 유지할 수 있었고, 90m가 그동안 형성한 이전 경로는 통과하지 못했다.
90m의 탐색은 약 11ms였으므로 그 반례를 시간 예산 소진만으로 설명할 수 없다.
**더 긴 구간이 현재 계산뿐 아니라 이후의 이전 경로·초기값도 바꾸므로, 전역적으로 더 낫지는 않다.**

동일 cap의 반복에서도 모양이 달라지는 경우가 있었다. 첫 원본의 60m 반복은 638/696,
90m 반복은 626/696 출력 CRC가 같았지만, 진단 실패 집합은 각각 완전히 같았다.
최초 차이의 trace에서는 같은 이전 경로·score·mask 상태에서 70ms 예산 분기가 갈려,
한쪽만 추가 seed를 계산하고 새 경로를 채택했다. 근거리 10m 안에서도 경로 차이가 있었다.
이는 시간 제한 후보 탐색의 비결정성 근거이지, 실제 차량이 그만큼 옆으로 튀었다는 측정은 아니다.
두 번째 원본의 같은 cap 반복은 각각 800/800 출력 CRC까지 일치했다.

후속 원문은 `planner_logs/analysis/261028_v99_cap_replay/`에 보존했다.
`source60_cap60_vs90_repeat.json`, `source90_cap60_vs90.json`과 독립 `bag_audit/`의
개선·반례 그림을 함께 읽는다. 최초 고정 입력 성공만 골라 운영 승격 근거로 쓰지 않는다.

## 운영 결정과 보존 자료

운영 파일의 cap은 60m, 두 tracker 후보는 OFF로 유지한다. 새 PR/병합·모델 재학습은 하지 않았다.
현재 소스와 달랐던 로컬 tracker·traffic 판단 plugin만 정상 증분 build/install로 맞췄다.
이 설치와 cap90 승격은 별개이며 MPT/BPP 바이너리는 네 시험에서 동일했다.
추가 승격 판단은 안정된 시간축의 LAN 주행 또는 실제 동일 입력 대조와 함께 한다.

- 원본 실행: `planner_logs/validation/window90_v99_e12_{clear,crate}_cap{60,90}_261028_*/`
- 시험 입력·실행 전 검사·독립 감사·설치 receipt: `planner_logs/analysis/261028_window90_live/`
- 상세 CSV·trace·속도/경로 그림·원본 시계 대조: `planner_logs/analysis/261028_duplicate_213815/live_cap_compare/`
- 완성된 원본 전방 영상과 재구성 BEV: `planner_logs/analysis/261028_window90_live/video_crate_cap{60,90}_v3/`

데스크톱 녹화의 RViz 렌더 영역이 검정으로 저장되어, 비교용 BEV는 bag의 기록값으로 재구성한다.
그것은 실제 RViz 녹화나 충돌 GT가 아니다. 전방 영상은 bag에 들어 있던 원본 JPEG다.
두 비교 영상은 10fps·H.264로 정상 마감됐고 준비 대기를 제외한 실제 주행을 담았다.
원본 데이터·GT·모델·기존 실행 기록과 사용자의 다른 미커밋 변경은 보존했다.
