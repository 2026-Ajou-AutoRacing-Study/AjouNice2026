## 3. 중복 장애물 신고의 원인 분리

카메라와 LiDAR에서 문제 위치는 한 개의 나무 상자였다. 검출기 자체가 404프레임 중 4회 두 박스를 출력했다.
두 박스의 BEV IoU는 약 .082/.417/0/.457로 운영 NMS .50보다 낮았다.
특히 한 번은 중심이 1.616m 떨어져 IoU가 0이므로 NMS만 조금 강화해 해결할 수 없다.

가장 중요한 불일치는 **장애물의 출력 속도는 0인데 내부 CTRV가 위치를 계속 전진시킨 것**이다.
신고의 두 번째 UUID `…0185`는 57개 출력에서 속도 0이었지만 위치 차분 속도 중앙값은 10.54m/s였다.
사각 상자의 yaw·중심 오차가 숨은 속도/회전 추정과 결합해 실제 장애물보다 차량 쪽으로 이동했다.

| 기록 사건 | bag 시작 후 |
|---|---:|
| 첫 장애물 `…0183` SOA 기억 | 26.258초 |
| 첫 MPT 최적화 실패 | 26.453초 |
| 두 번째 `…0185` 확정 / SOA 기억 | 30.012 / 30.052초 |
| 차체와 장애물 여유영역 겹침 경고 | 31.803초 |
| perception 빈 출력 | 33.544초 이후 |

따라서 **최초 감속 전부가 두 번째 ID 때문은 아니다.** 중복은 후반 여유영역 침범을 악화시킨 요인이다.
SOA는 UUID별 장애물을 후방 통과까지 기억하고 단순 미수신 TTL은 두지 않는다.
유령 ID가 없어져도 기억이 남을 수 있지만, 남아 있다는 것만으로 항상 영구 정지/DNF라고 단정하지 않는다.
진짜 가려진 장애물을 삭제할 수 있어 blanket TTL이나 안전 마진 축소는 하지 않았다.

새 371초 기록에서도 같은 상자 부근 UNKNOWN 두 ID가 약53.3초 공존하고 나중 ID의 Vehicle 분류도 관측됐다.
그 긴 공존 구간의 정차는 실제 적색 신호 대기였으며 중복 때문에53초 정지한 것이 아니다.
두 번째 track의 출생 검출 score도 .708로 높아 낮은 score의 새 ID만 막는 규칙으로 일반화할 수 없다.
그 기록은 후방 통과 시 SOA 기억을 해제했고 구 bag과 같은 지속 긴급제동은 관측되지 않았다.
중복 현상의 독립 재현이지 모든 장면의 정지 원인이 같다는 증거는 아니다.

### 적용하지 않은 간단한 대안

- NMS IoU .50→.45/.40: 독립 14장면에서 실제 장애물의 0.5m 이내 매칭도 줄었고 IoU 0 중복은 남는다.
- obstacle score .10→.15: 신고 구간의 유효 검출 47프레임 중 7개를 잃는다.
- birth guard 거리 .75→1.2m: 별개의 근접 장애물까지 합치는 음성 대조가 재현됐다.
- 작은 박스로 birth guard 확대: 실제로 떨어진 작은 객체 두 개를 지우는 대조가 재현됐다.

E12/E24도 같은 원본 12입력을 다시 비교했다. E24는 중복 프레임이 적지만 한 번 누락하고,
한 상자를 score .674의 차량으로 분류하므로 모델 원복이 해결책이라는 결론은 나오지 않는다.
E12에서는 정상 위치 후보가 .098, 어긋난 후보가 .109인 프레임이 있어 .10 문턱 아래로 정상 후보만 사라졌다.
박스 개수 감소 자체를 정확도 개선으로 세지 않는다.
실제 데이터 로더/온라인 전처리의 12개 입력 RGB·정규화 픽셀·XYZI는 일치했다.
동일 E12 eager 두 실행은 bit-exact가 아니지만 매칭한 박스 XY 차이 최대0.20mm, score 차이 최대 .000311이었다.
당시 모델/가속 경로 receipt가 없어 기록과 eager의 차이를 TRT 한 요소로 단정하지 않는다.

후보 A는 출력 사본의 UNKNOWN pose만 유지한다. 내부 연결은 정확히 같지만 유령 ID 오차가 일부 악화돼 단독 승격하지 않는다.

정상 ID의 XY p95 .611→.296m를 보였다. 두 UUID 자체가 완전히 없어진 것은 아니다.

Vehicle proxy는77.037→77.014%, 매칭되지 않은 차량 출력은158→183으로 소폭 악화됐다.

추가 음성 대조에서는 달리던 CAR가 UNKNOWN으로 잠깐 오분류되고 관측이 끊길 때 B의 ID 손실이 늘었다.

### 실제 플래너 체인 대조

같은 기록 ego·v97 map·route로 실제 설치된 BPP/SOA → smoother → MPT를 격리 재생했다.
BVP·Cruise·제어기·UDP·MORAI는 시작하지 않았다. source/hash/clock과 사용한 입력을 receipt에 보존했다.
첫 시도에서 비동기 ego 스냅샷 차이를 발견해, 해당 cycle의 실제 odom 수신 ACK를 맞춘 새 실행으로 검증했다.
엄격한 OFF A/A는380/380 cycle에서 odom·SOA geometry·BPP bounds·MPT 점·진단 등급이 일치했다.

- OFF: 최적화 실패7회. 초기26.3~26.8초6회 + 후반31.8초 차체 여유영역 겹침1회.
- 정지 prior: 초기6회는 그대로, 후반31.8초 실패는 없어졌다. 안전 마진·수명·planner 알고리즘은 그대로다.
- 해당 신고의 C 예측은1146개 tick·실제3개 후단 stage에서 이전 B와 직렬화 결과가 같아 위 대조를 그대로 적용할 수 있었다.
- 두 UUID/SOA 기억 자체는 남았다. 현재 MPT가 그 뒤 회복하는 것과 과거 전체 스택이 bag 종료까지 정지한 것을 구분한다.

고정 ego 재생이므로 실제 차가 새 궤적을 따라갔을 때의 완주·충돌·재제동은 아직 미검증이다.

**독립 자료에서 완전한 무퇴행이 아니므로, 장애물 개선 일부만 보고 production에 승격하지 않는다.**

### 최초 MPT 실패의 추가 조사

초기6회는 두 번째 ID 없이도 재현된다. 첫 두 cycle은 QP solve가 성공했으나 실제 출력 형상의 충돌 후검사에서 탈락했고,
100ms 예산 안에서 이전 방향의 재시도에 시간을 써 반대 방향을 못 보았다. 이후에는 양쪽 hard corridor 실패도 섞였다.
장애물이 reference상64~66m 전방일 때 회피/복귀에 필요한 창은 약86m인데 설정 cap은60m였다.
cap 경계의 종단 docking·선형화·후처리와의 조합이 조사 대상이며, 정확한 QP 해/기준점 기록 없이 단일 원인으로 확정하지 않는다.
soft 여유 .55m를 후검사에서 잘못 hard로 적용한 증거는 없다. 안전 마진을 줄이는 조치는 하지 않는다.
현재 설치 바이너리·원본 recorded prediction을 유지한 채 private config 한 값만60→90m로 바꿔 추가 대조했다.
380/380 cycle에서 ego·BPP 경로/경계·SOA 객체가 같고 resolved ROS 파라미터 차이도 해당 키 하나뿐이었다.

| 실제 MPT 고정 입력 대조 | cap60 | cap90 |
|---|---:|---:|
| 총 실패 | 7 | 1 |
| 초기26.3~26.8초 실패 | 6 | 0 |
| 후반31.8초 차체 여유영역 겹침 | 1 | 1 |
| MPT 처리 p95 / 최대 ms | 50.65 / 121.24 | 45.12 / 95.17 |
| 개별 solver 최대 ms | 55.51 | 78.43 |

초기 잘림 문제의 유력한 보완이다. 반복 재시도가 줄어 총 처리시간은 이 표본에서 늘지 않았지만,
큰 QP 한 번의 비용은 증가했다. 재생 harness의 대기 시간과 shared CPU까지 섞인 wall time을 실제 주행 Hz로 환산하지 않는다.
cap90을 새 프로세스에서 반복해380/380 cycle의 ego·BPP·SOA·MPT 점·진단 등급 일치를 확인했다.
초기6회 실패는 반복에서도0회였고 전체 처리 p95/max는46.24/82.27ms였다.
두 객체의 겹침 이후61개 cycle은 cap60/90/90반복 모두 추가 실패0·solve420회로 같았으며,
그 구간 처리 p95도64.12/62.45/66.73ms였다. 인지 출력 소실 이후50개 cycle의 solve401회도 같았다.
구간별 처리시간의 시점 정렬은 동일 순서 publication을 가정하며, header가 있는 search/solver trace와 함께 읽는다.
최신v99·다중 장애물·새 폐루프를 더 확인하기 전에는 production cap60을 변경하지 않는다.
후속 상태: [v99 로컬 폐루프 4회 대조](261028_V99_WINDOW60_90_LIVE_REVIEW.md)에서는 모두 완주했지만
90m의 우위를 확인하지 못했고 측위·시뮬레이션 시간축 교란도 있었다. 따라서 cap60 유지 결정은 그대로다.
추가 확인할 소스 설정은 `planning_ws/src/autoware_launch/config/ros1/planning/scenario_planning/lane_driving/motion_planning/autoware_path_optimizer/path_optimizer.param.yaml`의
`obstacle_optimization/max_forward_length`다. `return_length:15`·탐색100ms·마진 등은 이번 대조에서 유지했다.

단순히 ‘유효 incumbent가 없으면 이전 방향 우선 OFF’로 바꾸는1줄 대안은 채택하지 않는다.
짧지만 안전한 진행 중 회피의 방향 유지와 첫 성공 후 조기 종료도 함께 바뀌기 때문이다.
기존 방향 유지 회귀3개가 이 의미를 보호하며 cap90은 그 정책을 되돌리지 않고 초기 실패를 없앴다.

## 기록·현장 화면 개선

- 이후 개발용 녹화는 BVP·MPT·smoother·PI controller 실제 파라미터 namespace도 snapshot에 넣는다.
- 신호 관측과 `planner_decision_debug`의 분석 준비 상태를 별도로 표시한다. 과거 metadata는 덮어쓰지 않는다.
- 다음 녹화에는 vector map·route·운행 모드·차량 속도/조향도 포함하고 `planner_map_route_context`의 실제 기록 여부를 표시한다. 이번 새 bag에는 이 문맥 일부가 빠져 있었으며 현재 파일로 소급해 채우지 않는다.
- `field planning`은 실제 신고에 있던 ‘최적화 실패 후 기존 경로 제동’, ‘차체 여유영역 겹침’,
  ‘긴급제동 출력’을 한국어 한 줄로 구분한다. 실제 충돌/중복 원인을 자동 확정하지 않는다.
- 화면 요약·새 회귀 31개, recorder/launch/replay 계약44개 통과. 원문 stdout/stderr는 그대로 보존한다.
- 후단 전체 단위시험은177개 통과·rostest 전용1개 skip, 별도 격리 master의 실제 통합시험1개도 통과했다.
  팀의 현재10초/101pose를 거부하던 오래된 테스트 기대를 바로잡았으며 horizon runtime 값은 바꾸지 않았다.
- 최종 tracker native107개 통과, 후보 OFF는15개 native replay의 baseline state/prior covariance와 정확히 같다.
- 문서 검사에서 현재 링크323개·원문 snapshot13개는 확인됐고, 기존 `kcity_map/README.md`의126행/65행 budget 초과1건은 남아 있다. 이번 작업에서 지도 문서를 임의 재정리하거나 검사 기준을 낮추지 않았다.

MORAI·메인 ROS master·실행 중인 제어 스택을 재시작하지 않았다. 시험은 소유한 격리 master/프로세스만 사용했다.
모델·threshold·NMS·제동계수·지도·SOA 마진/수명은 유지한다.
마감 준비상태 조회에서는 MORAI/validator GUI만 실행 중이고 실제 센서·측위·계획·제어 publisher와9090 bridge는 없었다.
이것을 네트워크 단절이나 현재v97 실행으로 단정하지 않는다. 종료된 시험의 ROS 파라미터와 실제 실행 노드를 구분하며 새 폐루프 시험을 완료했다고 보고하지 않는다.
