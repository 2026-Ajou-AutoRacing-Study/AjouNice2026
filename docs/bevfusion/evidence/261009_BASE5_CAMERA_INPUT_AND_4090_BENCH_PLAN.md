# Base5 RTX 4090 입력 후보 비용 시험 계획

2026-10-09의 설계 검토 기록이다. 이후의 실제 입력·pooling 검증과 최신 전달 번들은
[입력·pooling 최적화 근거](261010_BASE5_INPUT_POOL_OPTIMIZATION_EVIDENCE.md)를 따른다.
아래 ‘수집 중’, ‘번들 미구현’, ‘미측정 추정’은 이 계획을 작성한 당시의 상태다.
현재 Sunny13 수집과 production E25는 유지한다. 수집 도중에는 이미지 입력 크기,
crop, resize, GT 정책이나 collector runtime을 바꾸지 않는다.

목표는 Base5-only Sunny13 5K 및 환경별 새 배치로 확장할 6 환경 30K의 카메라 입력을
선택하는 것이다. 본학습을 해상도별로 여러 번 완료할 시간은 없으므로 입력 구도 검토와
짧은 비용 시험으로 후보를 줄이고, 본학습은 선택한 설정으로 한 번 진행한다.
384×1056은 종전 비용 비교 후보이지 확정된 학습 설정이 아니다. CPU crop 분석 후 우선
후보는 **448×896 아래 정렬**, 비용 대안은 384×896, 원거리 밀도 대안은 512×1056이다.
다음 작업은 현재 수집을 유지한 채 추천 후보의 전처리·투영 및 GT 재선별을 검증하는 것이다.
팀원용 새 시험 번들 제작과 업로드는 그 이후에 진행한다.

crop 크기와 위치, 카메라별 처리, GT visibility 및 투영 정합의 조사 기준은
[별도 카메라 crop 조사 계획](261009_BASE5_CAMERA_CROP_INVESTIGATION.md)으로 분리했다.
이 문서는 비용 실측과 추정, 학습시간 예산, 팀원용 번들 범위만 관리한다.
아래 초기 비용 표는 종전 비례 해상도 비교 기록이며 현재 시험 후보는 후반 표를 따른다.
가중치 초기화, 기존 pooling의 cache와 BEVPoolv2 방식 검증 및 수집 중 작은 CUDA 시험은
[별도 실행 계획](261009_BASE5_INITIALIZATION_AND_RUNTIME_OPTIMIZATION_PLAN.md)을 따른다.
아래 MORAI 종료 조건은 전체 모델 비용 시험의 조건이며 작은 연산 correctness 시험과 구분한다.

## 수집 종료 후 해상도 선택 기준

2026-10-09 20:49 KST 대화 정리. 이번 수집 종료 뒤 crop·투영 정합과 cache/분리 pooling의
출력 정합을 확인하고, 최적화 전후 비용을 측정한 다음 학습할 세로×가로 입력을 확정한다.
TensorRT 성공을 전제로 큰 입력을 선택하지 않는다. 세로 확대에 따른 시야 보존과
가로 확대에 따른 원거리 픽셀 밀도를 함께 비교하며 해상도만으로 AP 개선을 보장하지 않는다.

13Hz 입력 간격은 약 76.9ms다. 평균 모델 시간이 70ms가 될 때까지 입력을 최대화하지 않는다.
전처리 포함 평균 50~60ms는 첫 시험의 여유 있는 목표이며 고정 합격선은 아니다.
p95/p99, 밀집 장면, 실제 입력 시각부터 객체 발행까지의 지연과 drop을 확인한다.
latest-only 처리는 오래된 입력의 누적을 막지만 모든 13Hz 입력의 처리를 보장하지 않는다.
독립 비용 시험과 최종 ROS/full-stack 검증을 구분하며 CPU/GPU 병렬 작업 시간을 단순 합산하지 않는다.

| 전처리 포함 평균 목표 | 세로×가로 후보의 개략 예상 | 해석 |
|---|---|---|
| 50ms 전후 | 448×896 | 안정성 우선 후보 |
| 60ms 전후 | 512×1056 | 원거리 픽셀 밀도와 실시간성의 균형을 노리는 후보 |
| 70ms 전후 | 576×1152 | 불확실성이 큰 확장 탐색 후보이며 필수 시험이나 기본 목표가 아님 |

이 표는 TensorRT 없이 cache/분리 pooling 등으로 전처리 포함 전체 시간을 20~30% 줄일 수
있다고 가정한 **미측정 외삽**이다. 기존 320×896의 50.93ms만 실측이다. 같은 고정
voxel/camera BEV/depth 간격을 가정하며 최종 4-class 비용으로 인증한 값도 아니다.
최적화율은 해상도에 따라 달라질 수 있다. 아래 비최적화 모델 추정과 이 표를 실측처럼 합치지 않는다.
576×1152는 전처리/crop 정합과 stride 제약부터 검증해야 하며 기존 분석·번들 후보에 자동 추가하지 않는다.

최종 입력과 crop 위치는 실측·시야 보존·짧은 학습 smoke로 정하고 PyTorch fallback을 남긴다.
동등한 출력의 추가 추론 최적화는 학습 중이나 학습 후에도 적용할 수 있다.

## RTX 4090 실측과 해상도 추정

[4090 반환 결과](261009_RTX4090_CAPACITY_RESULTS.md)의 실측은 3-class, batch 1 AMP,
voxel 0.075m, camera BEV 0.30m, depth 0.50m, 종방향 ±100m와 횡방향 ±30m 비용 대조다.
이 계획을 작성할 당시 Base5 코드 후보는 4-class, voxel 0.10m, camera BEV 0.40m, depth 1.0m이므로
같은 모델의 실측이 아니다. 최종 간격 선택은 남아 있으며 새 시험에서는 모든 해상도에
동일한 공간과 depth 설정을 사용한다. 격자를 성기게 하여 해상도 증가 비용을 상쇄하지 않는다.

| 이미지 | 320 대비 픽셀 수 | 4090 모델 평균 | CPU 준비 포함 | 학습 비용 배수 예상 |
|---|---:|---|---|---|
| 320×896 | 1.00× | 45.86ms 실측 | 50.93ms 실측 | 기준 |
| 384×1056 | 1.41× | 55~65ms 추정 | 60~72ms 추정 | 1.2~1.4× |
| 448×1248 | 1.95× | 68~82ms 추정 | 74~90ms 추정 | 1.5~1.8× |
| 512×1408 | 2.51× | 85~105ms 추정 | 91~114ms 추정 | 1.8~2.3× |

미측정 행은 같은 원본에 대한 이미지 처리 비용 증가를 외삽한 개략 추정이다.
320 실측의 camera backbone/neck은 8.22ms, camera에서 BEV 변환은 21.56ms이며,
나머지 약 16.08ms를 일정하게 둔 `16.08 + 29.78 × pixel_ratio`를 중심값으로 삼았다.
CPU 준비 포함 값에도 ROS 통신, publish, tracker, planner는 들어가지 않는다.

## 학습시간과 정확도의 판단

4090에서 학습시간은 아직 실측하지 않았다. 기존 5060Ti의 256×704, 작은 ROI pilot은
batch 4에서 약 0.52초/step이었지만 4090 확대 모델에 그대로 적용하지 않는다.
추론의 GPU 간 속도 비율을 학습 속도 비율로 사용하지 않는다.

대화 중의 초기 예산 추정은 30K 중 train 25,530과 val 4,470, 단일 4090, AMP,
로컬 SSD, 20epoch의 train 처리만 가정하여 320은 20~50시간, 384는 24~70시간,
448은 30~90시간, 512는 36~115시간이었다. 배치 효율, VRAM, loader의 불확실성이
커서 보장값이나 실측 ETA가 아니다. 검증과 rosbag 평가는 별도로 필요하며 짧은 학습
측정 후 갱신한다. 20epoch를 best checkpoint의 필요조건이나 고정 학습 계획으로
결정한 것은 아니다.

원거리 전후방 차량과 작은 객체의 존재 및 class 검출에는 고해상도의 이점이 있을 수
있지만 이번 비용 시험으로 AP 개선을 판정하지 않는다. 화면 밖으로 잘린 부분, LiDAR
점 부족, 학습 분포 부족은 해상도만으로 해결하지 않는다. 384×1056은 초기 비용 비교
후보이며 현재 우선 crop 추천이 아니다. 추천 shape의 변경이 정확도 개선이나 기존
학습시간 추정의 성립을 보장하지도 않는다.

## 팀원용 딸깍 시험 범위

별도 Git clone이나 전체 dataset 다운로드 없이 필요한 코드, 설정, 소량의 실제 이미지,
LiDAR, GT를 동봉한다. 기존 Docker와의 호환성 및 checksum을 확인하고 다운로드,
압축 해제, `run.sh`, 결과 ZIP 전달만으로 실행할 수 있도록 만든다. 새 번들은 아직
구현하거나 업로드하지 않았다.

| 해상도 | 추론 | 짧은 학습 | 용도 |
|---|---|---|---|
| 320×896 | 실시 | batch 1과 가능한 경우 2 | 기준 |
| 384×896 | 실시 | batch 1과 가능한 경우 2 | 비용 우선 대안 |
| 448×896 | 실시 | batch 1과 가능한 경우 2 | 근접·측방 시야 보존 우선 후보 |
| 512×1056 | 실시 | 우선 batch 1 | 원거리 밀도 확대 대안 |

모두 아래 정렬이며 네 카메라의 출력 shape는 동일하다. 전처리 정합 검증 후 번들에
반영한다. 동일 BEV 및 depth에서 단순 외삽한 모델 평균은 각각 약 46/52/58/72ms다.
320만 기존 실측이며 나머지는 해당 입력으로 실측한 값이 아니다. 512는 CPU 준비와
ROS 출력까지 포함하면 13Hz 예산이 부족할 수 있어 p95와 실제 step 비용을 우선 확인한다.

추론은 원거리뿐 아니라 근접과 밀집 장면의 동일 raw를 사용하고 모델 단독과 CPU 전처리
포함 시간을 평균/p50/p95/p99로 분리한다. 학습은 실제 GT로 forward, backward,
optimizer step까지 측정한다. AMP와 batch를 기록하고 warmup은 통계에서 제외한다.
비정상 loss나 지속적인 AMP step skip을 정상 학습 속도로 취급하지 않는다.
OOM은 해당 조건만 실패로 남기고 다음 조건을 진행한다. 최대 VRAM, 환경, 설정,
로그, 표, 원본과 입력 비교 이미지 및 실제 시험 소요 시간을 ZIP 하나로 묶는다.

pooling 최적화가 correctness를 통과하면 동일 입력의 baseline/cache A/A+B를 추가 비교한다.
입력 크기 효과와 구현 효과를 분리하며 geometry 재생성 cold와 cache hit warm 비용도 기록한다.
추론 cache의 이득을 backward/optimizer 이득으로 가정하지 않는다. 새 adapter 검증 전에는
기존 3-class checkpoint 비용 대조와 최종 4-class Base5 학습 step을 같은 결과로 표기하지 않는다.

MORAI와 다른 학습은 끈다. 풀스택은 이번 시험에서 보류한다. MORAI가 별도 PC이면
GPU 경합은 줄지만 CPU 전처리, 신호등 GPU 추론, RViz, 통신과 대기열의 영향까지
없어지는 것은 아니다. Planning 처리시간을 BEVFusion GPU 시간에 그대로 더하지도
않는다. 13Hz 주기는 약 76.9ms이며 평균 모델 70ms만으로 실시간성을 인증하지 않는다.
이번에는 독립 실행 비용만 측정하고 실제 ROS 출력과 풀스택 회귀는 별도 검증으로 남긴다.

| 준비된 번들의 자동 작업 | 예상 시간 |
|---|---:|
| 환경과 파일 확인 및 샘플 준비 | 1~3분 |
| 네 해상도 로딩과 warmup 및 추론 | 3~6분 |
| 네 해상도 batch 1 학습 측정 | 3~8분 |
| 가능한 세 해상도 batch 2 학습 측정 | 3~6분 |
| 표와 이미지 및 ZIP 생성 | 1~2분 |
| 전체 | 약 10~30분 |

다운로드와 Docker 설치 시간을 제외한 준비 단계 추정이다. 시험 step 수와 반복 수를
동결한 뒤 실제 소요 시간을 기록한다. 첫 연산 초기화나 OOM 복구가 길면 늘어날 수 있다.
정확도나 최종 학습 수렴 시험이 아니므로 여러 후보 측정이 본학습 여러 회를 뜻하지 않는다.
