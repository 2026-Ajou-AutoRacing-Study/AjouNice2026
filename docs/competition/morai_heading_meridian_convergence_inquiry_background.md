# MORAI heading 문의문 배경 설명

이 문서는 `morai_heading_meridian_convergence_inquiry.md`가 무슨 뜻인지, 왜 그런 방식으로
작성했는지를 좌표계를 처음 접한 사람도 이해할 수 있도록 설명한다.

## 1. 우리가 발견한 현상

대회 시나리오 파일에는 차량의 시작 방향이 `62.515 deg`라고 적혀 있었다. 그런데 MORAI가
ROS로 보내준 차량 heading은 `63.862 deg`였다.

```text
63.862 - 62.515 = 1.347 deg
```

처음에는 MORAI가 차량 방향을 약 `1.347 deg` 잘못 보내는 버그라고 생각했다.

MORAI 측에서는 다음과 같은 가능성을 제시했다.

- 차량을 Spawn하면서 scenario 파일과 실제 자세가 조금 달라졌을 수 있음.
- 차량이 도로에 묻히지 않게 z 위치를 조정하는 과정이 있음.
- IMU heading bias가 누적되어 localization 위치가 틀어질 수 있음.

하지만 이 설명만으로는 우리가 측정한 현상을 설명하기 어려웠다.

## 2. 왜 Spawn 오차가 아니라고 보는가

Spawn 오차라면 보통 차량을 처음 생성한 위치에서만 차이가 나타나거나, 차량이 도로에
정렬되는 과정에 따라 값이 조금씩 달라져야 한다.

하지만 실제로는 다음과 같았다.

- 출발점뿐 아니라 2.2 km 전체 주행에서 같은 차이가 나타남.
- 차량이 여러 방향으로 회전해도 약 `1.347 deg` 차이가 유지됨.
- 정지 상태의 155개 sample에서 heading 값의 표준편차가 `0 deg`였음.

특히 z는 차량의 높이 방향이고 yaw는 위에서 내려다봤을 때의 회전 방향이다. 차량을 땅에
묻히지 않게 z를 조금 올렸다는 설명은 일정한 yaw 차이가 발생한 직접적인 이유가 되기
어렵다.

## 3. 왜 IMU bias 누적도 아니라고 보는가

IMU bias는 센서가 아주 조금 틀린 값을 계속 측정하면서 시간이 지날수록 추정 오차가
커지는 현상이다. 예를 들어 방향을 매초 조금씩 잘못 적분하면 10초보다 100초 후의 위치
오차가 더 커질 수 있다.

하지만 이번 문제는 다음과 다르다.

- 오차가 시간에 따라 증가하지 않고 처음부터 끝까지 거의 일정함.
- IMU를 전혀 사용하지 않아도 같은 결과가 나옴.

IMU 대신 `/Ego_topic.position`의 연속된 두 위치를 연결하면 차량이 실제로 어느 방향으로
이동했는지 계산할 수 있다.

```text
이전 위치 ●────────▶ ● 다음 위치
                  실제 이동 방향
```

이렇게 position만으로 계산한 이동 방향과 `/Ego_topic.heading`을 비교해도 약 `1.346 deg`
차이가 났다. 반대로 heading에서 `1.347 deg`를 빼면 중앙값 오차가 약 `0.000735 deg`로
줄었다.

따라서 문제의 원인은 IMU 하나가 잘못 측정한 것이 아니라, position이 속한 map 좌표계와
heading의 기준 방향이 서로 다르기 때문일 가능성이 높다.

## 4. True north와 grid north란 무엇인가

우리가 흔히 말하는 북쪽에도 서로 다른 기준이 있다.

### True north

지구의 실제 북극을 향하는 방향이다. 나침반·GPS·INS에서 사용하는 지리적인 기준과
관련된다.

### Grid north

둥근 지구를 평면 지도에 옮긴 뒤, 지도의 세로 격자가 가리키는 북쪽이다. UTM map에서
사용하는 XY 축의 북쪽이라고 생각하면 된다.

지구는 둥글지만 지도는 평면이기 때문에 대부분의 위치에서 두 북쪽은 완전히 일치하지
않는다.

```text
                 true north
                      ↑
                      │
                      │  약 1.348 deg
                      │ /
                      │/
                 grid north
```

이 두 방향 사이의 각도를 **자오선 수렴각**이라고 한다.

## 5. 왜 0.001 deg 일치가 강한 증거인가

K-City 시작 GPS 좌표를 WGS84 UTM Zone 52N으로 계산하면 자오선 수렴각은
`-1.34805590 deg`이다.

MORAI ROS heading에 이 값을 적용하면 다음과 같다.

```text
ROS heading                   63.86204529 deg
UTM 자오선 수렴각을 적용     -1.34805590 deg
------------------------------------------------
계산된 grid yaw               62.51398939 deg
Scenario yaw                  62.51500000 deg
차이                           0.00101061 deg
```

차량 Spawn 오차나 임의의 센서 bias가 우연히 해당 GPS 위치의 자오선 수렴각과
`0.001 deg` 수준으로 일치할 가능성은 매우 낮다. 전체 주행의 position-derived course까지
같은 결론을 보인다는 점을 합치면 자오선 수렴각이 원인이라는 증거는 매우 강하다.

## 6. 그러면 MORAI 값은 버그인가

여기서는 표현을 조심해야 한다.

다음과 같이 설계했다면 각각의 숫자는 수학적으로 모두 정상일 수 있다.

```text
Scenario·MGeo map yaw  → grid north 기준
Ego·Competition·IMU    → true north 기준
```

True north와 grid north가 다른 것 자체는 버그가 아니다. 문제는 참가자에게 다음 정보가
명확하게 제공되지 않았다는 점이다.

- 각 heading이 어느 north를 기준으로 하는가?
- map frame에 사용할 때 누가 변환해야 하는가?
- 어떤 UTM zone과 datum을 사용해야 하는가?
- 수렴각의 부호와 공식은 무엇인가?

따라서 가장 정확한 표현은 다음과 같다.

> 자오선 수렴각은 정상적인 지리 좌표계 현상이지만, 서로 다른 heading 기준을 같은 yaw처럼
> 제공하면서 변환 계약을 명시하지 않았다면 대회 인터페이스의 좌표계 명세 누락 또는 통합
> 문제이다.

## 7. 왜 다른 팀은 문제를 제보하지 않았을 수 있는가

다른 팀도 같은 현상을 겪었다고 확정할 수는 없다. 하지만 같은 launcher와 map을 사용한다면
공통적으로 존재할 가능성이 높다.

그럼에도 제보가 없었던 이유로 다음 가능성을 생각할 수 있다.

1. `1.347 deg`는 RViz에서 눈으로 보기에는 매우 작음.
2. GNSS 위치를 EKF에 계속 넣으면 필터가 위치 오차를 반복해서 줄여줌.
3. NDT·ICP·map matching이 map 기준으로 yaw를 다시 맞출 수 있음.
4. 팀 내부에서 상수 offset을 넣고 별도로 제보하지 않았을 수 있음.
5. 좌표 변환 라이브러리가 자오선 수렴각을 이미 적용했을 수 있음.
6. 정량 평가 없이 차량이 경로를 대략 따라가는지만 확인했을 수 있음.

즉 “다른 팀이 제보하지 않았다”는 사실은 자오선 수렴각 가설을 반박하지 않는다. 다만 다른
팀이 문제를 몰랐다고 확정해서도 안 된다.

## 8. MORAI 개발진이 알고 있었는가

MORAI 내부 개발진의 인식은 외부에서 확인할 수 없다. 따라서 “개발진도 몰랐다”고 단정하면
안 된다.

다만 최초 답변에는 다음 내용만 있었다.

- Spawn 과정의 차이.
- z 여유값.
- IMU bias 누적.

True north, grid north 또는 자오선 수렴각은 언급되지 않았다. 정말 이 현상을 즉시
인지했다면 보통은 “Scenario는 grid north, ROS heading은 true north”라고 설명하는 것이
가장 직접적이다.

따라서 문의문에서는 다음 정도로만 표현했다.

> 최초 답변 단계에서는 이번 현상의 직접 원인이 자오선 수렴각임이 아직 식별되지 않았을
> 가능성이 있다.

핵심 simulator 개발자는 알고 있지만 문의 담당자에게 전달되지 않았을 수도 있고, 각 모듈이
서로 다른 정상 좌표계를 사용하면서 통합 문제를 인지하지 못했을 수도 있다. 어느 쪽인지는
공식 답변으로 확인해야 한다.

## 9. 왜 문의문을 공격적으로 쓰지 않았는가

우리에게 중요한 것은 “누가 몰랐는가”를 따지는 것이 아니라 대회 전에 좌표계 계약을
확정하는 것이다.

“MORAI가 명백히 틀렸다”고 단정하면 상대는 simulator 내부 값이 각 좌표계에서 정상이라는
이유로 방어할 수 있다. 반대로 수치를 제시하고 reference를 질문하면 다음 중 하나를 공식
답변해야 한다.

1. 서로 다른 north 기준을 의도적으로 사용했고 참가자가 변환해야 함.
2. 원래 같은 기준이어야 하는데 변환이 누락됨.
3. 현재 분석과 다른 공식 좌표계 정의가 있음.

어느 답을 받아도 localization 구현에 필요한 정보가 생긴다. 그래서 문의문의 중심을
상대방의 실수 여부가 아니라 다음 재현 사실에 두었다.

- 고정된 `1.347 deg` 편차.
- 전체 주행 position-derived course 검증.
- UTM 자오선 수렴각과 약 `0.001 deg` 일치.
- localization에 미치는 실제 오차.

## 10. 우리 코드에서는 어떻게 처리해야 하는가

공식 답변 전에는 현재 K-City에서 검증된 다음 보정을 유지하는 것이 안전하다.

```text
map_yaw_deg = received_heading_deg - 1.347 deg
```

하지만 최종 구현은 상수를 여러 노드에 직접 넣는 방식보다 다음 구조가 좋다.

```text
수신 heading의 reference 확인
              ↓
현재 GPS와 map projection으로 convergence 계산
              ↓
true north heading을 grid north yaw로 한 번만 변환
              ↓
localization·TF·Lanelet에서 동일한 map yaw 사용
```

공식 답변으로 모든 대회 구간에서 같은 고정값을 쓰도록 명시된다면 상수 보정도 가능하다.
그러나 일반적인 구현으로는 위치에 따라 자오선 수렴각을 계산하고, 변환이 중복 적용되지
않도록 localization 입력 경계 한 곳에서 처리하는 것이 가장 안전하다.
