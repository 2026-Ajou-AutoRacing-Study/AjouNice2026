# PO 최적화 범위와 최종 발행 형상 수정

## 결론

19:14:32 백에서 재현한 핵심 결함은 짧은 QP 뒤의 기준 경로 연결부가 장애물을 관통하는데, 앞부분 QP를 반복해서 풀던 것이다. 40점은 뒤쪽 이력까지 포함하므로 이 사례의 유효 전방 길이는 약 15m였다. 충돌은 약 21m 앞, 최적화 범위 밖에 있었다. 솔버 교체나 timeout 연장만으로 해결할 문제가 아니다.

기존 분석의 실제 주행 정지 원인과 재생의 후보 탈락 원인은 구분한다. 실제 백 후반의 측정 차체/관측 마진 중첩은 새 프로세스 재생에서 동일하게 재현되지 않았다. 기록 시작 전 SOA 상태가 완전히 복원되지 않기 때문이다.

## 이번에 적용한 코드

1. 기본 40점·0.5m를 유지하되 장애물 후단, hard/soft margin, 차량 길이, 복귀 15m까지 필요한 전방 최적화 길이를 계산한다. 최대 전방 길이는 60m이며, 뒤쪽 이력에 필요한 점은 별도로 확보한다. 따라서 장애물이 있는 경우 실제 QP 점 수는 40보다 커질 수 있다. 이는 단순히 40점을 고정하는 기존 설정의 결함을 바로잡기 위한 변경이다.
2. 전체 연결·재샘플링·형상 검사를 통과한 경로를 그대로 선택하고 발행한다. 선택 후 다시 연결해서 검증 당시와 다른 형상이 되는 처리를 제거했다. 이전 경로도 마지막 검증 완료 발행 형상을 기준으로 쓴다.
3. 현재 관측 및 현재 자세로 재검증된 이전 후보가 있으면 새 해 탐색에 실패해도 이를 유지한다. 이전 경로의 속도는 최신 입력 속도로 갱신한다. 실제 형상 검증 실패까지 무시하는 변경은 아니다.
4. 최적화 범위 뒤에서 충돌한 후보는 같은 seed의 재선형화를 중단한다. 재시도 시간 예산을 incumbent 유무와 관계없이 각 시도 사이에 적용한다. 한 번 시작한 솔버 실행을 중단하는 hard timeout은 아니다.
5. QP에 실제 들어갈 점만 도로/차체 경계를 계산하도록 잘라 불필요한 경계 계산을 줄였다.

주요 소스: `planning_ws/src/autoware_path_optimizer/src/node.cpp`, `src/mpt_optimizer.cpp`, `include/autoware/path_optimizer/{common_structs,node}.hpp`. 설정에 `obstacle_optimization/max_forward_length=60.0`, `return_length=15.0`을 추가했다. Release 빌드 및 install 완료.

이미 변경한 smoother 조향 레이트 40deg/s, controller source timeout 10초, 거리 기반 종방향 속도 목표는 유지했다. 이번 수정으로 충돌 검사나 도로 제약을 완화하지 않았다.

## 검증

### 마지막 원본 백 전체 파이프라인 재생

원본: `planning_rviz_20260924_191432.bag`, 16.323초. 현재 남아 있는 원본 백은 이 파일 하나이므로 이전 15개 전체에 대한 재검증을 주장할 수 없다.

최종 빌드, 추가 진단 환경변수 없이 재생:

처리시간은 개선됐지만 안정적인 10Hz 발행을 달성했다는 뜻은 아니다. 첫 수정본의 별도 반복 재생에서는 p95 76.9ms, 최대 85.2ms, 발행 간격 최대 162.7ms였다. 입력 도착과 callback 실행, 각 주기 계산시간 편차를 포함한 발행 간격은 별도 문제다. Python 관측자의 수신 간격 최대 386.9ms 및 header age 최대 369.0ms를 PO 계산시간으로 해석하지 않는다. stage 검사기의 `stale_header_frames`는 50ms 기준 통계이며 controller의 10초 source timeout 실패 판정과 다르다.

BPP와 path smoother 기준 경로는 장애물을 관통하는 108프레임이 그대로 있다. 현재 구조에서는 PO가 독립 장애물 제약으로 회피를 만드는 입력 기준 경로이므로, 이를 최종 회피 실패 108건으로 세지 않는다. PO 이후 단계에서 따로 검사했다.

**재생 후반 저속까지 해결됐다는 증거는 아니다.** 이 백은 원래 차량이 멈춘 위치·속도를 계속 주입한다. 최종 재생 12초 이후 목표속도는 약 0.9004km/h였으며 smoother engage_velocity=0.25m/s와 같은 수준이다. 기록된 정지 상태를 사용하는 재생으로 실제 차량이 계속 가속·복귀할 것이라고 입증할 수 없다. 첫 수정본과 최종 반복의 속도 수치도 달라져, 한 번의 수치만으로 주행속도 개선을 확정하지 않는다.

## 적용 및 남은 확인

추가 빌드는 필요 없다. 실행 중인 플래닝 노드는 이번 설치 바이너리를 다시 로드하도록 재시작해야 한다. 이번 작업은 운영 프로세스를 재시작하지 않았다.

새 MORAI 주행에서 PO → 최종 목표속도 → controller target/brake → 실제 속도를 다시 맞춰야 한다. 특히 실제 추종 오차가 있는 복귀 구간, 동적 관측 형상 변경, 최대 발행 간격을 확인해야 한다. 이번 결과의 범위는 재현된 연결부 결함 수정, 마지막 백 재생, 합성 장면 및 이상적 전진 검사다.
